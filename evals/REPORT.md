### `test_budget.py::test_search_returns_a_valid_plan`: fail

['mid: Below the quick-win share', 'mid_quick60: Below the quick-win share']
assert not ['mid: Below the quick-win share', 'mid_quick60: Below the quick-win share']

Analysis (from reading the code, not measured): engine/greedy.py stops adding quick wins at the quick-win share in its first phase and only ends above the share if later additions happen to be quick wins, so it can finish a fraction of a percent under; agents/repair.py then marks that plan invalid ('Below the quick-win share') because it requires the full share. When the greedy plan is invalid the loop needs a valid AI plan; the offline proposer's candidates are dropped as repeats of greedy's own site set or fall under the share too. ## How the search was driven

The agents' search loop calls `summary` and `layer`, which are not implemented on this branch, and the evals must not call them. `evals/evalkit/adapter.py` answers those two reads from the loaded area and meta.json and passes everything else to the engine's public API unchanged. `rescore` is never cached. Greedy and the per-site results are computed once in worker processes by the same engine functions, to save wall time; sites the canopy rule rejects are reported to the loop as not usable (the engine's own `single_site` raises InvalidChangeError for them, checked on the tiny fixture, which the loop's site catalog does not expect). Search runs use a long time limit so the wall clock cannot change what a run does.
